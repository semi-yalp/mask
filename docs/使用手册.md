# sql-mask 使用手册

> 配套文档：《功能清单》（全部功能面清点）、《端到端使用指南》（47.100.166.158
> 已部署环境的实操步骤）。本文讲「怎么用」：构建、配置、五种使用姿势与运维。

## 1. 架构一图流

```
                    ┌──────────────────────────────────────────────┐
                    │            frontend 管理台 (nginx:80)         │
                    │  总览/访问管理/策略管理器/试验台/审计/设置      │
                    └───────┬──────────────┬───────────┬───────────┘
              /api/rewrite  │ /api/instances,/api/effective│ /api/audit
                    ┌───────▼──────┐  ┌────▼─────────┐ ┌─▼──────────┐
                    │ mask-core    │  │ policy-server │ │ (audit 走   │
                    │ 8080 改写+CLI │◀─│ 8081 策略服务  │ │  core 8080) │
                    └───────┬──────┘  └────┬─────────┘ └────────────┘
                            │              │
                    ┌───────▼──────────────▼──────┐
                    │   /api/rewrite/instances/*  │
                    │   /api/metadata/instances/* │
                    │        mask-query 8083       │
                    │  改写→JDBC 执行→只回脱敏结果   │
                    └───────┬─────────────────────┘
                            │
   ┌─────────────┐   ┌──────▼───────────────┐
   │ mask-metadata│   │  业务数据库引擎        │
   │ 8082 表结构   │──▶│  PG/MySQL/Trino/…    │
   └─────────────┘   └──────────────────────┘
```

- **改写服务（mask-core，8080）**：只解析/校验/血缘/改写/输出 SQL，从不执行业务 SQL。
- **策略服务（mask-policy-server，8081）**：实例、策略、UDF 的管理面 + 按主体编译的生效配置数据面。
- **元数据服务（mask-metadata，8082）**：引擎连接信息与表结构的唯一事实源。
- **查询服务（mask-query，8083）**：唯一受控执行面——改写不可绕过，只返回脱敏结果。

## 2. 构建与启动

```bash
# 全量测试（含嵌入式 PG 全链路 QueryEndToEndTest，约 +2 分钟）
mvn test

# 打包（产出各 fat jar）
mvn package
# mask-core/target/sql-mask.jar                          改写服务+CLI（双模式）
# mask-policy-server/target/mask-policy-server-*.jar     策略服务
# mask-metadata/target/mask-metadata-*.jar               元数据服务
# mask-query/target/mask-query-*.jar                     查询服务
```

前端（本机无需 Node 时用 deploy.sh 在构建机执行；或直接 npm 构建）：

```bash
cd frontend
npm install && npm run build      # 产出 dist/
bash deploy.sh up                 # 或：构建镜像并启动 nginx（端口 80）
docker compose -f docker-compose.frontend.yml up --build
```

## 3. 五种使用姿势

### 3.1 最快上手：单 jar 内联改写（不连任何数据库）

```bash
java -jar mask-core/target/sql-mask.jar --metadata metadata.yaml \
  --sql "SELECT phone FROM customer"
```

输出（PostgreSQL 方言）：

```sql
SELECT phone FROM (SELECT customer.phone AS phone FROM customer) AS t WHERE ...
-- 实际形态：原始查询为内层，最外层对命中列调用 UDF：
SELECT "mask_phone"(t0.phone, 3, 4) AS phone FROM (SELECT ...) AS t0
```

### 3.2 Web 内置页面（单 jar）

```bash
java -jar mask-core/target/sql-mask.jar          # http://localhost:8080
```

页面提供：表结构编辑（增删改表/列）、从数据库导入（PG/MySQL/Trino）、列策略绑定、
策略定义、YAML 源码双向编辑、执行改写（逐语句结果 + 已脱敏/原样标记 + 错误码）。

### 3.3 CLI 全参数

见《功能清单》§5。常用组合：

```bash
# Ranger 式策略文件 + 查询主体
java -jar sql-mask.jar --metadata metadata.yaml --policies policies.yaml \
  --user alice --groups devs --sql "SELECT phone FROM customer"

# 从策略服务拉编译配置（instance 模式）
java -jar sql-mask.jar --instance pg_prod --policy-service http://localhost:8081 \
  --user alice --sql "SELECT phone FROM customer"

# 连库导出表结构骨架
java -jar sql-mask.jar --pull-metadata --host 10.0.0.5 --database crm \
  --user postgres --password '***' --output crm.yaml
```

### 3.4 REST API（curl）

```bash
# 内联模式
curl -s localhost:8080/api/rewrite -H 'Content-Type: application/json' -d '{
  "metadataYaml": "metadata:\n  tables:\n    - catalog: crm\n      schema: public\n      name: customer\n      columns:\n        - {name: id, type: bigint}\n        - {name: phone, type: varchar}\n  policies: {}",
  "sql": "SELECT phone FROM customer",
  "dialect": "postgresql"
}'
# → {"statements":[{"ordinal":1,"originalSql":"...","rewrittenSql":"...","masked":true}],"rewrittenSql":"..."}

# instance 模式（配置来自策略服务；方言以实例 dialect 为准，忽略请求 dialect）
curl -s localhost:8080/api/rewrite -d '{"instance":"pg_prod","sql":"...","user":"alice","groups":["devs"]}' -H 'Content-Type: application/json'
```

### 3.5 管理台前端（nginx 80，生产形态）

浏览器打开控制台 → 设置页填双 Key → 访问管理建实例 → 策略管理器配策略/UDF →
试验台改写 → 审计查看。实操见《端到端使用指南》。

## 4. 配置文件

### 4.1 metadata.yaml（表结构 + 可选内嵌策略）

```yaml
metadata:
  tables:
    - catalog: crm          # 必填；PG=库名，Trino=catalog
      schema: public        # 必填
      name: customer        # 必填
      rowFilter: "status = 'active'"   # 可选：行过滤（内嵌模式）
      columns:
        - {name: id, type: bigint}     # 名称+类型必填
        - {name: phone, type: varchar}

columns:                    # 可选：列→策略绑定（内嵌模式）
  - {catalog: crm, schema: public, table: customer, column: phone, policy: phone_mask}

policies:                   # 内嵌模式必填顶层键（只用行过滤时写 {}）
  phone_mask:
    udf: mask_phone
    arguments: [3, 4]       # 有序标量，原样渲染进 UDF 调用
```

规则：列策略用完整 `catalog.schema.table.column` 精确匹配（不支持通配/search_path）；
策略键折叠小写；SQL 引用的所有表必须在 `metadata.tables` 声明；非限定名在多个
schema 同名时按 schema 字母序静默取第一（请用全限定名避免歧义）。

### 4.2 policies.yaml（Ranger 式，与内嵌策略互斥）

```yaml
policies:
  - name: mask-customer-phone
    enabled: true
    priority: 0
    resources:
      - catalog: crm
        schema: public
        table: customer
        column: [phone, email]      # 标量、列表或 "*"（支持 glob："phone_*"）
    dataMaskItems:
      - groups: ["*"]               # 或 users: [...]；至少一个非空
        udf: mask_phone
        arguments: [3, 4]

  - name: filter-archived-orders
    resources:
      - {catalog: crm, schema: public, table: orders}   # rowFilter 到表级，不带 column
    rowFilterItems:
      - groups: ["*"]
        filterExpr: "status <> 'archived'"
```

要点：
- 一条策略只能有 `dataMaskItems` 或 `rowFilterItems` 之一；
- 主体特异性：user 精确 > group 精确 > `*`；请求未带主体视为匿名（仅 `*` 命中）；
- 多策略命中同列：disabled 跳过 → priority 高者 → 声明序，每列唯一命中；
  行过滤命中项 AND 叠加；
- 资源四级都支持 glob；策略资源必须命中至少一张声明表，否则 `CONFIG_ERROR`（fail-closed）；
- `filterExpr` 白名单：声明列引用/字面量/AND·OR·NOT/比较/IS [NOT] NULL/
  IS [NOT] DISTINCT FROM/IN 常量/四则运算；函数、子查询、CURRENT_USER 等全禁止；
  三值逻辑按 SQL 语义（`region = 'north'` 会排除 NULL 行，需要保留 NULL 用
  `region IS NOT DISTINCT FROM 'north'`）。

### 4.3 行过滤注入形态

引用受控表的每个位置替换为 `(SELECT * FROM <表> WHERE <rowFilter>) AS <别名>`；
在聚合、去重、排序、分页与写入之前生效；过滤谓词始终使用明文列。

## 5. 策略服务（8081）使用

### 5.1 全流程 REST

```bash
BASE=http://localhost:8081
KEY='-H X-Api-Key:local-admin-key'    # 配置了 SQLMASK_ADMIN_API_KEY 时需要

# 1) 建实例（带表结构）
curl -s $BASE/api/instances -H 'Content-Type: application/json' $KEY -d '{
  "name":"pg_prod","dialect":"postgresql",
  "tables":[{"catalog":"crm","schema":"public","name":"customer",
    "columns":[{"name":"id","type":"bigint"},{"name":"phone","type":"varchar"}]}]}'

# 2) 注册 UDF 签名（对齐引擎侧重载；首参=被脱敏列值）
curl -s $BASE/api/instances/pg_prod/udfs -H 'Content-Type: application/json' $KEY -d '{
  "name":"mask_phone",
  "signatures":[{"params":["varchar","integer","integer"],"returns":"varchar"},
                {"params":["bigint","integer","integer"],"returns":"varchar"}]}'

# 3) 建策略（DATAMASK / ROW_FILTER；subjects 声明主体）
curl -s $BASE/api/instances/pg_prod/policies -H 'Content-Type: application/json' $KEY -d '{
  "name":"mask-phone","policyType":"DATAMASK","isEnabled":true,"priority":0,
  "resource":{"catalog":"crm","schema":"public","table":"customer","columns":["phone"]},
  "subjects":{"users":[],"groups":["*"]},
  "udf":"mask_phone","arguments":[3,4]}'

# 4) 按主体拉生效配置（数据面 Key）
curl -s "$BASE/api/effective/pg_prod?user=alice&groups=devs" -H 'X-Api-Key: local-data-key'
```

### 5.2 从元数据服务一键导入表结构

```bash
curl -s $BASE/api/instances/pg_prod/import-metadata -H 'Content-Type: application/json' $KEY -d '{
  "metadataBaseUrl":"http://localhost:8082",
  "metadataApiKey":"local-dev-key",
  "metadataInstance":"pg_prod"}'
# 实例不存在则按快照 dialect 自动创建；已存在则校验方言一致并整体替换表
```

### 5.3 instance 模式接入改写服务

mask-core 环境变量：`POLICY_SERVICE_URL`、`POLICY_SERVICE_API_KEY`（数据面 Key）。
进程内 LRU(256) 缓存按主体缓存编译配置，每 30s（`POLICY_SERVICE_POLL_INTERVAL_MS`）
轮询刷新；策略服务短暂不可用时继续用缓存（stale-but-available），无缓存时绝不降级。
紧急止血：`POST /admin/cache/refresh`（可带 `{"instance":"..."}`）。

## 6. 元数据服务（8082）使用

```bash
BASE=http://localhost:8082
H='-H X-Api-Key:local-dev-key -H Content-Type:application/json'

# 1) 登记实例（密码用环境变量名引用，不落库）
curl -s $BASE/api/instances $H -d '{
  "name":"pg_prod","dialect":"postgresql","engine":"postgresql",
  "connection":{"host":"10.0.0.5","port":5432,"database":"crm",
                "dbUser":"postgres","passwordRef":"SQLMASK_DS_PG_PROD_PASSWORD"}}'

# 2) 在线采集（服务端解析 passwordRef；连接只读系统目录）
curl -s -X POST $BASE/api/instances/pg_prod/collect $H

# 3) YAML 导入（hive/sparksql 只能走这里；带 rowFilter 的表声明会被拒）
curl -s $BASE/api/instances/import $H -d '{"name":"hive_prod","dialect":"hive","metadataYaml":"..."}'
```

数据面（供 policy/query 消费）：`GET /api/metadata/instances`、
`GET /api/metadata/instances/{name}`、`GET /api/metadata/instances/{name}/version`。

## 7. 查询服务（8083）使用

前提：引擎侧已安装脱敏 UDF（PG `CREATE FUNCTION`、Hive/Spark `CREATE FUNCTION …
USING JAR`、Trino SPI 插件、StarRocks Java UDF、MySQL 存储函数）。

```bash
export SQLMASK_DS_PG_PROD_PASSWORD='***'      # passwordRef 指向的密码
curl -s localhost:8083/api/v1/query -H 'Content-Type: application/json' \
     -H 'X-Api-Key: local-query-key' -d '{
  "instance":"pg_prod",
  "sql":"SELECT name, phone FROM customer WHERE id < 5",
  "user":"alice","groups":["devs"],
  "maxRows":1000,
  "includeRewrittenSql": true
}'
# → {"columns":[...],"rows":[["张*丰","138****5678"],...],"rowCount":...,
#     "masked":true,"rowFiltered":false,"elapsedMs":...,"rewrittenSql":"..."}
```

护栏：仅单条 SELECT（写语句 `WRITE_STATEMENT` 拒绝）；超时 30s；maxRows 硬上限 10000；
每实例并发 10，超出 `QUERY_BUSY` 快速失败；重写服务不可达时 fail closed。

## 8. 引擎侧 UDF 部署前提

| 引擎 | 安装方式 | 最小示例（PostgreSQL） |
|---|---|---|
| PostgreSQL | `CREATE OR REPLACE FUNCTION`（SQL/PL-pgSQL） | 见《端到端使用指南》§7 |
| MySQL | 存储函数 `CREATE FUNCTION` | `CREATE FUNCTION mask_phone(v TEXT, f INT, b INT) RETURNS TEXT ...` |
| Hive | `CREATE TEMPORARY FUNCTION … AS 'class' USING JAR 'path'` | 去掉 TEMPORARY 即永久 |
| Spark | `CREATE [OR REPLACE] FUNCTION … AS 'class' USING JAR 'path'` | — |
| StarRocks | 3.x Java UDF | — |
| Trino | SPI 函数插件部署 plugin 目录后重启 | — |

聚合列（如 `count(phone)`）命中文本型策略时，包装目标是数值——需要
`mask_phone(bigint, integer, integer)` 这类重载，否则真库执行报类型错误。

## 9. 鉴权一览

| 服务 | 变量 | 未配置时行为 |
|---|---|---|
| mask-core | `SQLMASK_REWRITE_API_KEY`（`/api/rewrite/instances/*`） | 放行（本地开发） |
| mask-core | `SQLMASK_ADMIN_API_KEY` / `SQLMASK_DATA_API_KEY`（`/api/instances`、`/api/effective`、`/api/audit`，存量分支） | 放行 |
| policy-server | `SQLMASK_ADMIN_API_KEY`（管面）/ `SQLMASK_DATA_API_KEY`（`/api/effective`） | 放行 |
| mask-metadata | `METADATA_API_KEY` | **全 401（fail-closed）** |
| mask-query | `SQLMASK_QUERY_API_KEY` | **全 401（fail-closed）** |

Key 一律走 `X-Api-Key` 头；比较为常量时间。前端控制台在「设置」页保存两把 Key
（管理/数据，localStorage），API 调用自动携带。

## 10. 审计与指标

审计（core/metadata 异步尽力而为写 ES；队列满丢弃，ES 故障不影响业务请求）：

```bash
docker compose -f docker-compose.metadata.yml up -d elasticsearch   # 本地起 ES（127.0.0.1:9200）
curl -s 'http://localhost:8080/api/audit/events?eventType=REWRITE&size=10'
curl -s 'http://localhost:9200/_cat/indices/mask-audit-*?v'
```

事件类型：`REWRITE`（每改写请求恰一条）/ `ADMIN_CHANGE`（管理面变更）/
`EFFECTIVE_PULL`（生效拉取，可关）/ `QUERY`（查询执行）。环境变量前缀
`AUDIT_`，见《功能清单》§9。

指标：各服务 `/actuator/prometheus`（前缀 `sqlmask_`，无鉴权，仅内网）；
本地验证 `docker compose -f docker-compose.metrics.yml up -d` 后起 Prometheus 抓 8080/8082。

## 12. 故障排查速查

| 症状 | 原因与处理 |
|---|---|
| 400 `CONFIG_ERROR`：策略来源必须唯一 | metadata 内嵌策略与 `policyYaml`/`--policies` 同时给了——二选一 |
| 400 `UNSUPPORTED_STATEMENT` | UPDATE/DELETE/递归 CTE/根级集合操作/输出位关联子查询 |
| 400 `LINEAGE_UNKNOWN` | 输出列来源无法安全追踪（如输出位置标量子查询） |
| 400 `PARSE_ERROR`（MySQL） | 用了双引号字符串/标识符（MySQL 方言双引号直接拒） |
| Hive/Spark `PARSE_ERROR`：`default.customer` | `DEFAULT` 是保留字，写反引号 `` `default`.customer `` |
| 聚合列真库执行类型错误 | UDF 缺数值重载（需 `mask_phone(bigint,int,int)`）或别对聚合列绑文本策略 |
| `QUERY_BUSY` / 503 | 该实例并发满 / 语句容器超时（被取消） |
| `CREDENTIAL_UNAVAILABLE` | passwordRef 指向的环境变量在查询服务进程里不存在 |
| `AUDIT_SEARCH_UNAVAILABLE`（502） | ES 不可用或未部署（业务不受影响） |
| instance 模式改写用旧配置 | 30s 轮询未到；急用 `POST /admin/cache/refresh` |
| CLI 退出码 2 | 用法错误（看 stderr 提示；`--sql/--input` 二选一、`--groups` 不能与 `--pull-metadata` 同用） |
| 前端页面 401 | 设置页未填 Key 或 Key 与服务端不一致（metadata/query 服务未配 Key 时全 401 是 fail-closed 设计） |
